# Torium local accounts, keyrings, and faucet

Everything in this guide is for `torium-localnet-1` only. Local `tTOR` is
valueless, deterministic automation keys are public/disposable, and no local
key or mnemonic may be reused on a public or valuable network.

The chain uses one canonical 18-decimal ledger:

- EVM address: `0x` plus 20 bytes;
- Cosmos account address: the same 20 bytes encoded as `torium1...`;
- base denomination: `atorium`;
- display denomination: `tTOR`;
- `1 tTOR = 1000000000000000000 atorium`.

An EVM wallet and `toriumd` therefore see the same balance. These are two
address encodings and client surfaces, not two accounts or assets.

## Prerequisites

Start the default container localnet:

```bash
./chain/localnet/torium-localnet start
```

For native CLI work, build with the pinned Go 1.25.9 toolchain:

```bash
make -C chain/app build
export TORIUMD="$PWD/chain/app/build/toriumd"
export TORIUM_HOME="$PWD/chain/localnet/.state/client"
mkdir -p "$TORIUM_HOME"
```

The default container profile launches the faucet automatically. The optional
raw-process profile keeps process control explicit; after starting its
validators, run the binary in a second terminal. Its defaults bind both faucet
and RPC to loopback:

```bash
./chain/localnet/torium-localnet start --backend raw
./chain/app/build/torium-faucet
```

Keep client keyrings separate from validator homes. The whole
`chain/localnet/.state/` tree is ignored, but a validator-profile reset does
not delete the separate `client` directory. Ignored local state is still not a
backup; remove the client directory explicitly when it must be discarded.

## Choose a keyring deliberately

| Backend | Use | Security and lifecycle |
| --- | --- | --- |
| `os` | Interactive manual testing on a supported desktop | Uses the operating-system credential store. It may show system prompts and is unsuitable for headless CI. |
| `file` | Encrypted, portable local keyring | Prompts for its password on every access. Never embed the password in a script or environment variable. |
| `test` | Non-interactive tests only | Stores keys insecurely. Use only under disposable ignored state and delete it after the test. |

Never use a validator home as a client keyring. Do not put mnemonics, raw
private keys, passwords, or exported key files in Git, shell history, CI logs,
issues, screenshots, faucet requests, or environment files.

## Create, recover, list, and inspect accounts

Create a random manual-test account. `keys add` prints a mnemonic once; store it
only in an approved offline secret store if recovery matters, then clear the
terminal.

```bash
$TORIUMD keys add alice --home "$TORIUM_HOME" --keyring-backend os
```

Recover a local-only mnemonic interactively:

```bash
$TORIUMD keys add alice --recover --home "$TORIUM_HOME" --keyring-backend os
```

List and inspect public account information:

```bash
$TORIUMD keys list --home "$TORIUM_HOME" --keyring-backend os --output json
$TORIUMD keys show alice --home "$TORIUM_HOME" --keyring-backend os --output json
ALICE_BECH32=$($TORIUMD keys show alice -a --home "$TORIUM_HOME" --keyring-backend os)
```

Convert between EVM and Cosmos forms. Remove `0x` before parsing a hex address;
the first returned format is the `torium1...` account address.

```bash
EVM_ADDRESS=0x1111111111111111111111111111111111111111
$TORIUMD keys parse "${EVM_ADDRESS#0x}" --output json
$TORIUMD keys parse "$ALICE_BECH32" --output json
```

## Import and export

The preferred encrypted interchange format is the CLI's armored key export.
Both commands prompt for passwords. Keep the export outside the repository.

```bash
$TORIUMD keys export alice \
  --home "$TORIUM_HOME" --keyring-backend os \
  > /path/outside-the-repository/alice.asc

$TORIUMD keys import alice /path/outside-the-repository/alice.asc \
  --home "$TORIUM_HOME" --keyring-backend os
```

`unsafe-import-eth-key` and `unsafe-export-eth-key` expose raw Ethereum private
keys. They exist only for disposable local automation and wallet-tool
interoperability. Do not use them for a retained manual account.

Deterministic automation accounts must be derived inside the test process from
a clearly local, valueless domain, imported into a dedicated `test` keyring,
and deleted at the end. The faucet acceptance suite demonstrates this without
printing its raw key:

```bash
make -C chain/tests/faucet test
```

Manual test accounts should instead be randomly generated by `toriumd`, a
wallet, or `cast wallet new`. Never treat committed development fixture
addresses as private accounts; their keys are intentionally reproducible.

## Fund through the local faucet

The default Compose profile exposes the faucet only at
`http://127.0.0.1:8080`:

```bash
./chain/localnet/torium-localnet faucet "$EVM_ADDRESS"
./chain/localnet/torium-localnet faucet "$EVM_ADDRESS" \
  --amount-base-units 2500000000000000000 --json
```

The strict HTTP API is also available directly:

```bash
curl --fail-with-body http://127.0.0.1:8080/v1/fund \
  -H 'content-type: application/json' \
  --data '{"address":"0x1111111111111111111111111111111111111111"}'
```

`POST /v1/fund` accepts only `address` and optional decimal-string
`amountBaseUnits`. It never accepts or returns a mnemonic, private key, keyring
password, or raw signed transaction. Success contains the recipient, amount,
transaction/block hashes, block number, nonce, EIP-1559 type, and receipt
status. This is a normal signed chain transaction, not an off-chain balance
edit.

The local policy is:

- default `10 tTOR`, minimum `1 tTOR`, maximum `25 tTOR` per request;
- 30-second cooldown per address;
- maximum `100 tTOR` per address in a rolling one-hour process-local window;
- 4 KiB request bodies and 45-second transaction confirmation timeout.

The signer is the public deterministic genesis `faucet` fixture, derived only
in memory. Compose supplies no key volume, key file, mnemonic, or private-key
environment variable. Limits reset when the process restarts. This is
intentionally insufficient for the internet: a follow-up workstream owns the isolated signer,
persistent distributed quotas, abuse controls, monitoring, and incident
response required by a public faucet.

## Compare EVM, REST, and CLI balances

```bash
ALICE_EVM=0x1111111111111111111111111111111111111111
ALICE_BECH32=$(
  $TORIUMD keys parse "${ALICE_EVM#0x}" --output json | jq -r '.formats[0]'
)

cast balance "$ALICE_EVM" --rpc-url http://127.0.0.1:8545

curl --fail --silent \
  "http://127.0.0.1:1317/cosmos/bank/v1beta1/balances/$ALICE_BECH32/by_denom?denom=atorium" |
  jq '.balance'

$TORIUMD query bank balance "$ALICE_BECH32" atorium \
  --grpc-addr 127.0.0.1:9090 --grpc-insecure --output json
```

All three amounts must match in base units.

## Build and sign without broadcasting

Generate an unsigned bank transfer, then sign it offline. Supply the real
account number and sequence before broadcasting; `0` is only a disposable
format example.

```bash
$TORIUMD tx bank send alice "$ALICE_BECH32" 1atorium \
  --generate-only --chain-id torium-localnet-1 \
  --home "$TORIUM_HOME" --keyring-backend os --output json \
  > /tmp/torium-unsigned.json

$TORIUMD tx sign /tmp/torium-unsigned.json \
  --from alice --offline --account-number 0 --sequence 0 \
  --chain-id torium-localnet-1 \
  --home "$TORIUM_HOME" --keyring-backend os --output json \
  > /tmp/torium-signed.json

$TORIUMD tx broadcast /tmp/torium-signed.json \
  --node tcp://127.0.0.1:26657 --output json
```

Delete temporary transaction files afterward. A signed transaction is not a
private key, but it authorizes the exact encoded action.

## Transfer, staking, and governance

Send a bank transaction:

```bash
$TORIUMD tx bank send alice "$RECIPIENT_BECH32" 1000000000000000000atorium \
  --chain-id torium-localnet-1 --node tcp://127.0.0.1:26657 \
  --gas 200000 --fees 200000000000000atorium \
  --home "$TORIUM_HOME" --keyring-backend os --yes --output json
```

Inspect validators, delegate one whole 18-decimal power-reduction unit, and
query the result:

```bash
$TORIUMD query staking validators \
  --grpc-addr 127.0.0.1:9090 --grpc-insecure --output json

$TORIUMD tx staking delegate "$VALIDATOR_OPERATOR_ADDRESS" 1000000000000000000atorium \
  --from alice --chain-id torium-localnet-1 \
  --node tcp://127.0.0.1:26657 \
  --gas 250000 --fees 250000000000000atorium \
  --home "$TORIUM_HOME" --keyring-backend os --yes --output json

$TORIUMD query staking delegations "$ALICE_BECH32" \
  --grpc-addr 127.0.0.1:9090 --grpc-insecure --output json
```

Governance commands come from the exact Cosmos SDK v0.54 module descriptors.
Inspect the full local parameter object before building a proposal:

```bash
$TORIUMD query gov params \
  --grpc-addr 127.0.0.1:9090 --grpc-insecure --output json \
  > /tmp/gov-params.json
PARAMS=$(jq -c '.params' /tmp/gov-params.json)

$TORIUMD tx gov update-params-proposal "$PARAMS" \
  --deposit 1000000000000000000atorium \
  --title "Local governance exercise" \
  --summary "Valueless localnet parameter proposal" \
  --from alice --generate-only --chain-id torium-localnet-1 \
  --home "$TORIUM_HOME" --keyring-backend os --output json

$TORIUMD query gov proposals \
  --grpc-addr 127.0.0.1:9090 --grpc-insecure --output json

$TORIUMD tx gov vote "$PROPOSAL_ID" yes \
  --from alice --chain-id torium-localnet-1 \
  --node tcp://127.0.0.1:26657 \
  --gas 250000 --fees 250000000000000atorium \
  --home "$TORIUM_HOME" --keyring-backend os --yes --output json
```

The example deliberately keeps `--generate-only`. Remove it only when you
intend to mutate the disposable chain and have reviewed the full params,
deposit, voting period, and account funds.

## Reset and failures

`torium-localnet reset` deletes the selected validator runtime profile after an
explicit warning; it does not delete the separate `chain/localnet/.state/client`
keyring used in this guide. Delete that directory yourself only when intended.
A faucet restart clears its in-memory limit history. None of these operations
recovers a manual account.

The faucet returns `400` for malformed/unknown fields and invalid amounts,
`429` with `Retry-After` for limits, and `503` when it cannot confirm a chain
transaction. Do not retry `503` blindly without first checking the recipient
balance and known transaction state.
